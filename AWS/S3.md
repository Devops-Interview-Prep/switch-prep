# Amazon S3 — Simple Storage Service

> S3 is AWS's object storage service — infinitely scalable, 99.999999999% (11 nines) durability, accessed via HTTP. Used for static websites, data lakes, backups, ML datasets, application assets, and log archiving. Everything in S3 is an object, stored in a bucket.

---

## Core Concepts

```
Bucket: Top-level container (like a directory, but globally unique)
Object: A file + metadata stored at a key (path)
Key:    The "path" to an object within a bucket

S3 URI format:
  s3://bucket-name/key
  s3://my-app-logs/2024/01/app.log

Example:
  Bucket: my-company-data
  Key:    images/2024/01/logo.png
  URL:    https://my-company-data.s3.amazonaws.com/images/2024/01/logo.png

Key facts:
  - Buckets are per-region (but names must be globally unique)
  - Max object size: 5TB (use multipart upload for > 5GB)
  - No real folder hierarchy — keys just contain '/' characters
  - Default: up to 100 buckets per account (soft limit)
```

## Access Management

### IAM Policies (Identity-based)

```json
// Attached to IAM user/role — who can access which S3 resources
{
  "Effect": "Allow",
  "Action": ["s3:GetObject", "s3:PutObject"],
  "Resource": "arn:aws:s3:::my-bucket/*"
}
// Action wildcards: s3:* (all), s3:Get* (all reads), s3:Put* (all writes)
```

### Bucket Policies (Resource-based)

```json
// Attached to the bucket — controls cross-account access or public access

// Allow public read (for static website hosting):
{
  "Effect": "Allow",
  "Principal": "*",
  "Action": "s3:GetObject",
  "Resource": "arn:aws:s3:::my-public-bucket/*"
}

// Cross-account access — allow Role in Account B to read from Account A's bucket:
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Principal": {
      "AWS": "arn:aws:iam::222222222222:role/S3ReaderRole"
    },
    "Action": "s3:GetObject",
    "Resource": "arn:aws:s3:::account-a-data-bucket/*"
  }]
}
```

### Block Public Access

```
"Block all public access" = a safety guard on TOP of bucket policies/ACLs
- Enabled by default on new buckets
- Disabling it allows policies/ACLs to make content public
- Disabling does NOT automatically make bucket public
- Must also explicitly add a permissive bucket policy or ACL after disabling
```

## Object Ownership

```
Who owns an object when uploaded to your bucket?

By default: the UPLOADER owns the object, not the bucket owner.
Problem: Account A owns bucket, Account B uploads → Account B owns the object
         Account A cannot access/modify it without explicit ACL grant.

Settings:
  Object Writer (legacy default):
    → Uploader is always owner
    → Problems with cross-account uploads

  Bucket Owner Preferred:
    → Bucket owner automatically owns uploaded objects (if uploader grants it)
    → Still uses ACLs

  Bucket Owner Enforced (recommended):
    → Bucket owner always owns everything, ACLs are DISABLED
    → Use with bucket policies for access control
    → Simplest model for modern workloads
```

## CORS — Cross-Origin Resource Sharing

```xml
<!-- Required when frontend app on different domain reads from S3 directly -->
<!-- Example: React app on https://app.example.com fetches from S3 directly -->

<CORSConfiguration>
  <CORSRule>
    <AllowedOrigin>https://app.example.com</AllowedOrigin>
    <AllowedMethod>GET</AllowedMethod>
    <AllowedMethod>PUT</AllowedMethod>
    <AllowedHeader>*</AllowedHeader>
    <ExposeHeader>ETag</ExposeHeader>
    <MaxAgeSeconds>3000</MaxAgeSeconds>
  </CORSRule>
</CORSConfiguration>
```

## Storage Classes

| Storage Class | Access | Availability | Min Duration | Use Case |
|---|---|---|---|---|
| **Standard** | Frequent | 99.99% | None | Serving assets, hot data |
| **Intelligent-Tiering** | Unknown | 99.9% | None | Auto-optimize, unpredictable access |
| **Standard-IA** | Infrequent | 99.9% | 30 days | Backups, old logs |
| **One Zone-IA** | Infrequent | 99.5% | 30 days | Non-critical, reproducible data |
| **Glacier Instant** | Archive | 99.9% | 90 days | Medical records, media archives |
| **Glacier Flexible** | Archive | 99.99% | 90 days | Regulatory backups (1min-12hr retrieval) |
| **Deep Archive** | Cold archive | 99.99% | 180 days | Tax/legal data (up to 12hr retrieval) |

## Lifecycle Rules — Automatic Transitions

```json
{
  "Rules": [{
    "ID": "ArchiveLogs",
    "Prefix": "logs/",
    "Status": "Enabled",
    "Transitions": [
      {"Days": 30, "StorageClass": "STANDARD_IA"},
      {"Days": 90, "StorageClass": "GLACIER"}
    ],
    "Expiration": {
      "Days": 365
    }
  }]
}
```

```bash
# CLI commands:
# Upload with specific storage class:
aws s3 cp file.txt s3://my-bucket/ --storage-class STANDARD_IA

# List objects:
aws s3 ls s3://my-bucket/logs/

# Sync local directory to S3:
aws s3 sync ./dist s3://my-bucket/assets/ --delete

# Download:
aws s3 cp s3://my-bucket/file.txt ./local/

# Generate a pre-signed URL (time-limited access without credentials):
aws s3 presign s3://my-bucket/private-file.pdf --expires-in 3600
```

## Interview Q&A

**Q: What is the difference between IAM policies and bucket policies for S3 access?**
IAM policies are attached to identities (users, roles, groups) and define what that identity can do across all AWS resources — including S3. Bucket policies are attached to the bucket itself (resource-based) and define who can access that bucket from outside the account. For same-account access, either works. For cross-account access, you need a bucket policy on the target bucket (because IAM policies only apply within an account). Both use the same JSON policy language. The access decision is the union — if either allows it and neither denies it, access is granted.

**Q: When would you use S3 Intelligent-Tiering vs Standard?**
Intelligent-Tiering automatically moves objects between Frequent Access, Infrequent Access, and Archive tiers based on actual usage patterns — charging a small monthly monitoring fee per object (around $0.0025/1000 objects). Use it when access patterns are unpredictable or change over time, for datasets that are sometimes hot and sometimes cold. Use Standard when you know objects will be accessed frequently (avoids monitoring overhead) or when objects are small (monitoring fee per-object makes it less cost-effective for millions of tiny files).

**Q: What is an S3 Pre-signed URL and when do you use it?**
A pre-signed URL grants temporary, scoped access to a specific S3 object without requiring AWS credentials. Generated by your backend using `aws s3 presign` or the SDK, it embeds credentials and expiry time in the URL itself. The browser can use it directly. Use cases: (1) let users download private files directly from S3 without routing through your servers, (2) let users upload files directly to S3 (PUT pre-signed URLs) without your server handling the upload bytes. Time-limited: specify `--expires-in` in seconds. After expiry, the URL returns 403.
