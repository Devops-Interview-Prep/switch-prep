# Terraform Best Practices (with a real codebase as the mirror)

> The practices a tech lead enforces across a team, grouped by concern. Each one says what, why, and where the real platform repo in [Real-World/devops-platform](Real-World/devops-platform/) follows or breaks it, so the advice is anchored in code you can open. Interviewers do not want a list; they want the failure each rule prevents.

---

## 1. Repository and module structure

| Practice | Why | In the real repo |
|---|---|---|
| Three layers: resource modules, composition stacks, thin environment roots | Reuse at the bottom, opinions in the middle, blast radius at the top | Followed: `modules/`, `stacks/`, `environments/` |
| Split stacks by rate of change and blast radius | Network changes are rare and dangerous; add-ons change weekly; one state for both means every add-on bump risks the VPC | Followed: `01-network`, `02-eks-core`, `03-eks-platform` |
| One concern per module; no god-modules | A module that creates a DB, a bucket and an IAM user has three lifecycles and one blast radius | Mostly followed; `application-stack` is a composition and is fine; legacy `modules/eks/main.tf` monolith should go |
| No `provider` blocks in reusable modules | Blocks `count`/`for_each`, breaks multi-region, overrides root config silently | Broken in `stacks/application-stack/versions.tf` |
| Pin module sources by tag or commit | `main` moves under you | Local relative paths here (monorepo), which is fine; a registry with tags once two repos consume them |
| Keep environment roots free of logic | A root with `if` logic is a stack in disguise and cannot be generated by a UI or CI | Followed |
| Delete dead code | The next engineer copies the deprecated module | Broken: `modules/eks/main.tf` still present |

## 2. Variables, outputs, naming, tags

| Practice | Why | In the real repo |
|---|---|---|
| Every variable typed and described; `validation` on enums and formats | Fail at plan, not at apply; self-documenting | Followed widely (`nat_gateway_mode`, `condition_operator`); `list(any)` tolerations is the exception |
| Secure defaults; callers opt *out* of safety | The default is what 80% of callers get | Mixed: IMDSv2 and encryption yes; RDS `skip_final_snapshot = true` no |
| Use `optional()` object attributes for maps of config | One module serves many shapes without `try()` soup | Followed in `eks_addons` |
| Outputs expose IDs/ARNs/endpoints, not whole objects; mark only secrets sensitive | Stable interface; usable downstream | Broken in app roots (`output "stack_outputs" = module.app_stack`, all sensitive) |
| One `name_prefix` and one `common_tags` per stack, merged into every resource | Consistent names and cost allocation | Followed; S3 module drops `tags` (bug) |
| Mandatory tag set (`environment`, `service`, `owner`, `cost-center`, `managed-by`) enforced by `default_tags` and a plan policy | Untagged spend is unowned infrastructure | Partially: tags exist, nothing enforces them |
| Append account ID or region to globally unique names (buckets) | Collisions across accounts and environments | Followed in `application-stack` (`s3_name`) |

## 3. State

| Practice | Why | In the real repo |
|---|---|---|
| Remote state, one file per root, versioned, encrypted, public access blocked, locked | Shared safely, recoverable, no races | Followed; `use_lockfile = true` native locking |
| State is a secret: SSE-KMS with a CMK, TLS-only policy, scoped IAM, Object Lock for prod | State holds every sensitive attribute in plaintext | Partially: AES256, no bucket policy, no Object Lock |
| Never commit `*.tfstate*`, `*.tfplan`, `.terraform/` | Secrets and drift | Broken historically (removed in the sanitised copy) |
| Bootstrap the backend once with local state or by hand, document it | The backend cannot create itself | Followed: `bootstrap/` with a header comment |
| Cross-stack values via SSM parameters or scoped data lookups rather than `terraform_remote_state` | Decouples deploy order and output names; limits read of whole state | Broken: `terraform_remote_state` everywhere |
| Practise state surgery: `moved`, `import`, `state rm`, `force-unlock` only after checking the lock holder | Renames and adoptions without destroys | `import {}` blocks used for VPC adoption |
| Alarm on state bucket deletes and on `force-unlock` | Both are incidents | Not present |

## 4. Versions and dependencies

| Practice | Why | In the real repo |
|---|---|---|
| Modules declare minimum provider versions (`>= 5.0`); roots pin minors (`~> 5.40`); `required_version` everywhere | Modules stay reusable; roots are reproducible | Inconsistent: mix of `~>`, `>=` and none |
| Commit `.terraform.lock.hcl` with hashes for every platform CI and laptops use | Same provider bytes everywhere | Lock files were not committed |
| Provider and module bumps are their own PR with the changelog linked; roll dev → staging → prod | Majors rename and remove arguments | Not visible |
| Renovate/Dependabot opens the bump; a human reads the plan | Automation finds, humans decide | Not present |
| Pin Helm chart versions and EKS add-on versions in prod; float in dev deliberately | Discover breakage in dev, upgrade prod on purpose | Followed: prod tfvars pin add-ons; chart versions pinned |
| Pin AMI aliases (`al2023@v2025…`), not `latest` | Node fleets must not rotate on an upstream release | Broken in the Karpenter template |

## 5. Resources: the patterns that bite

| Practice | Why | In the real repo |
|---|---|---|
| `for_each` keyed by stable strings for collections; `count` only for on/off | Positional indexes re-create everything after a removal | Broken in subnets/routing; followed in access entries, add-ons |
| `lifecycle { prevent_destroy }` on stateful and allow-listed things (DBs, state bucket, NAT EIPs, KMS keys) | One bad plan should not be able to delete data | Missing |
| `create_before_destroy` on things referenced by others (SGs, launch templates) | Avoid "resource in use" failures | Followed on RDS/ALB SGs; launch template uses `latest_version` |
| `ignore_changes` only with a comment naming the other controller | Otherwise it hides a design problem | Followed in `emr-cluster` (managed scaling); documented need for MNG `desired_size` |
| Implicit dependencies via references; `depends_on` on modules only for real AWS ordering constraints | Module `depends_on` makes everything "known after apply" | Overused in stacks |
| `moved` blocks for refactors; `import` blocks for adoption, in reviewed PRs | Zero-destroy refactors; reviewed adoption | `import` used; `moved` not yet needed |
| `precondition`/`postcondition` for invariants (admin list non-empty, subnets span 3 AZs) | Fail at plan with a message | Missing (D16) |
| Separate the cluster from the things installed into it (providers configured from data sources in a second root) | Provider config cannot depend on a resource in the same plan | Followed: `02` vs `03` |
| Prefer EKS add-ons with `service_account_role_arn` over Helm for AWS-managed components | AWS tests the version matrix | Followed: CNI, CoreDNS, kube-proxy, CSI, Pod Identity agent as add-ons |

## 6. Security and secrets

| Practice | Why | In the real repo |
|---|---|---|
| Terraform should never see secret values: `manage_master_user_password`, IAM roles not keys, OIDC for CI, ESO at runtime | What Terraform sees lands in state and plan | Broken: `random_password` → state; one hardcoded password (removed) |
| Use `ephemeral` resources and write-only arguments (1.10+/1.11+) where a secret must pass through | Not persisted to state | Not yet used |
| No IAM users or access keys in modules; IRSA/Pod Identity per service; one role per service | Least privilege, attributable | Followed: `irsa-role`, scoped Karpenter policy |
| IMDSv2 required, hop limit 1, encrypted volumes, private endpoints, control-plane logs | The EKS hardening baseline | Followed |
| KMS: CMK per cluster/data class, rotation, explicit admin/user statements, `ViaService` | Blast radius and audit | Partially (root-only key policy) |
| Security groups by reference, egress narrowed in prod, DB tier without NAT | Primary network control | Partially (egress `0.0.0.0/0`) |
| Immutable ECR tags, scan on push, deploy by digest | Supply chain | Scan yes, mutable tags no |
| `bootstrap_cluster_creator_admin_permissions = false` with explicit access entries | No invisible admins | Followed |
| Scan: checkov/trivy, gitleaks, Access Analyzer policy validation in CI | Catch the known-bad before review | Missing |

## 7. Review, CI/CD and gating

The pipeline a tech lead installs, in order of value:

1. **Pre-commit:** `terraform fmt`, `validate`, `tflint` (AWS ruleset), `terraform-docs`, gitleaks.
2. **CI plan per changed root** with the plan artifact saved and a human-readable summary posted to the PR (Atlantis, Spacelift, env0, HCP Terraform, or GitHub Actions). Plan role is read-only plus `plan`.
3. **Static security:** checkov or trivy with an owned baseline; `skip` annotations need a reason and an expiry.
4. **Policy on plan JSON** (Conftest/OPA or Sentinel): region allow-list, no public EKS endpoints or buckets in prod, no `delete` of protected resource types, mandatory tags, IAM wildcard denial, cost delta threshold (Infracost).
5. **CODEOWNERS:** platform for `modules/` and `stacks/`, product plus platform for their roots, security for `iam/` and `kms/`.
6. **Apply the saved plan** from CI with an OIDC-assumed role; dev on merge, prod behind a named approval and a change ticket. Nobody applies from a laptop; break-glass pages.
7. **Drift:** nightly `plan -detailed-exitcode` per root; non-empty opens a ticket; reconciled within one business day.
8. **Evidence retained:** plan, policy results, approvals, apply log. This is the SOC 2 / ISO change-management control.

In the real repo: none of this exists yet in the tree (no `.pre-commit-config.yaml`, `.tflint.hcl`, `.checkov.yaml`, CODEOWNERS, PR template, workflow files). That is the first thing to add, and it is a better answer to "what would you change" than any single resource fix.

## 8. Testing

| Level | Tool | Use it for |
|---|---|---|
| Syntax/types | `terraform validate`, tflint | Every PR, pre-commit |
| Security/compliance | checkov, trivy, Conftest on plan | Every PR |
| Module logic | `terraform test` with mock providers (1.7+) | Module library: assert naming, policy ARNs (would have caught the EFS/EBS bug), conditional resources |
| Integration | terratest (Go) in a sandbox account | Core modules only (VPC, EKS cluster, RDS): apply, assert reachability/encryption, destroy; nightly or on release |
| Cost | Infracost | PR gate above a threshold |
| Drift | scheduled plan, driftctl, AWS Config | Daily |

Example `terraform test` for the IRSA module:

```hcl
# modules/iam/irsa-role/tests/trust.tftest.hcl
mock_provider "aws" {}

run "exact_subject_uses_string_equals" {
  variables {
    role_name = "t"  role_purpose = "t"
    oidc_provider_arn = "arn:aws:iam::123456789012:oidc-provider/oidc.eks.us-east-1.amazonaws.com/id/EXAMPLE"
    oidc_provider_url = "https://oidc.eks.us-east-1.amazonaws.com/id/EXAMPLE"
    service_account_subjects = ["system:serviceaccount:kube-system:ebs-csi-controller-sa"]
    managed_policy_arns = ["arn:aws:iam::aws:policy/service-role/AmazonEBSCSIDriverPolicy"]
  }
  assert {
    condition     = can(regex("StringEquals", aws_iam_role.this.assume_role_policy))
    error_message = "exact subjects must use StringEquals"
  }
}
```

## 9. Operations

- **Upgrades are code:** EKS version, add-on versions, chart versions, AMI alias all live in tfvars and move through dev → prod by PR. Never in the console.
- **Rollback plan per PR:** state the previous values; know which resources cannot roll back (EKS control-plane version).
- **Break-glass is allowed and loud:** console changes during incidents are announced and reconciled; CloudTrail alerts on write actions by non-CI roles.
- **Blast-radius drills:** run `plan` for every root after a provider bump; read the counts before the diff.
- **Delete with intent:** `terraform destroy` only on roots designed for it (ephemeral envs); `prevent_destroy` elsewhere; approvals for `delete` actions in prod via plan policy.
- **Document the TODOs in code** (as the `attach_cni_policy_to_node_role` description does), then track them.

## 10. Kubernetes from Terraform: where to stop

- Terraform installs what needs AWS IAM or must exist before GitOps: CNI/CoreDNS/kube-proxy/CSI as EKS add-ons, Karpenter, the LB controller, External Secrets Operator, ArgoCD itself.
- After ArgoCD is up, everything else is a Git-managed manifest: NodePools (day-2), Kyverno policies, namespaces and quotas, monitoring stack, applications.
- Avoid long-lived `helm_release` sprawl: Helm state in Terraform state plus Helm's own release secrets is two sources of truth, and `terraform destroy` of a cluster with Helm releases is slow and flaky (finalizers, webhooks).
- Never manage application Deployments in Terraform. See [What-To-Use-Terraform-For.md](What-To-Use-Terraform-For.md).

## Ten-line summary to memorise

1. Modules, stacks, roots; split by rate of change and blast radius.
2. Typed, validated, described inputs; secure defaults; minimal outputs.
3. One state per root; versioned, KMS-encrypted, locked, scoped; never in git.
4. Modules declare minimums, roots pin; lock file committed; Renovate bumps.
5. `for_each` over `count`; `prevent_destroy` on data; `ignore_changes` with a reason.
6. Terraform never sees secret values; roles not keys; IRSA/Pod Identity per service.
7. Plan on PR, policy on plan, saved-plan apply via OIDC, nobody applies from a laptop.
8. tflint + checkov + `terraform test` always; terratest for core modules.
9. Drift plan nightly; reconcile in a day; break-glass is loud.
10. Terraform stops at the control plane and IAM-needing add-ons; ArgoCD owns the rest.
